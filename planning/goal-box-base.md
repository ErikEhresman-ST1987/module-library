# Goal Box Base

**Type:** Reusable planning base  
**Purpose:** Define the currently approved mature destination and boundaries of a project before architecture or implementation planning.

A Goal Box is not a feature backlog, architecture document, or demand to build the mature product at once. It gives development a stable direction while leaving implementation and evidence-driven refinement free to evolve.

Use the smallest amount of structure that fully establishes the destination. Simple projects should remain simple. Add detail only when the project itself requires it.

## 1. Purpose and Core Promise

Describe why the project exists and the fundamental job, experience, or value it should provide.

State the primary user or player when that materially affects the design.

## 2. Mature Intended Experience

Describe what the successful mature version should actually feel like to use or play.

Prefer experiential language over implementation language.

## 3. Core Workflow or Experiential Loop

Describe the important complete loop or sequence the mature project must support.

This is not an implementation sequence. It establishes what must eventually work together for the project to fulfill its purpose.

## 4. Known Destination Capabilities

Record capabilities already known to belong in the mature destination.

Known destination requirements should influence foundational decisions when relevant even when their implementation is deferred.

Do not convert uncertain possibilities into requirements merely to make this section complete.

## 5. Foreseeable Scale and Environment

Record only scale, device, browser, offline, data, graphical, content, lifecycle, or similar expectations that could materially affect the foundation.

Do not invent speculative scale.

## 6. Governing Experience and Design Principles

Record the principles that must survive development.

These may include interaction character, visual identity, privacy, local ownership, pacing, accessibility, reliability, gameplay identity, or other project-specific qualities.

## 7. Explicit Non-Goals

State what this project is deliberately not becoming.

Non-goals prevent nearby attractive ideas from quietly changing the project or creating speculative infrastructure.

## 8. Intentionally Open Decisions

Record questions that should remain open until implementation, real use, playtesting, or better evidence makes the requirement concrete.

Leaving a decision open is preferable to manufacturing certainty.

## 9. Mature Experience Test

Write one concise governing question, plus only necessary supporting gates, that can test substantial future proposals against the intended destination.

The test should ask whether a proposal strengthens the actual experience rather than whether it adds capability.

## 10. Goal Box Boundary

The Goal Box defines the currently approved destination, protected core, boundaries, and important open questions.

It does **not** authorize implementation of the entire destination at once.

It does **not** predetermine every future increment.

It does **not** prevent evidence-driven change. When the user explicitly changes direction or real use reveals genuinely new information, revise the governing direction deliberately rather than quietly working around it.

Implementation should proceed through complete meaningful slices that advance or test the Goal Box while remaining diagnostically bounded.

---

## Authoring Rule

Start from the user's idea and actual requirements, not from this document as a questionnaire.

Do not ask the user questions already answered by the idea, existing project evidence, or governing documents. Ask only questions whose answers materially affect the mature destination, boundaries, known requirements, or intentionally open decisions.

The Goal Box is complete when the destination is clear enough to guide foundational decisions without pretending to know details that real implementation or use should decide.
